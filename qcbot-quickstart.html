1Two rule engines — how they work together
ENGINE 1 Predefined rules
59 built-in regex rules that scan your code line-by-line. Instant, offline, no API key needed. Every rule has a fixed ID, severity, and fix guidance.
CLI commands
qcbot check ./tests
Run all 59 rules — prints findings summary to terminal
qcbot check ./tests --report --threshold 80
Same + generate HTML report + exit code 1 if score < 80
qcbot check ./tests --stack pytest_api --json result.json
Different stack + write raw JSON output to file
qcbot check ./tests --disabled-rules PW-NMC-010,PW-CPX-003
Skip specific rules for this run
Browser UI
  • Load folder → Findings tab — all violations appear instantly
  • Toggle rules on/off in the Rules tab (per-stack, saved across sessions)
  • No setup required — works out of the box
ENGINE 2 AI rules (agentic)
AI reads your actual code and provides contextual explanations + corrected code. Also discovers new custom rules specific to your codebase. Requires an API key (Anthropic / Google / AWS Bedrock).
CLI commands
qcbot fix --file ./tests/login.spec.ts --rule PW-REL-001
Agent 3 — AI explains one finding + shows corrected code
qcbot remediate ./tests --severity critical --dry-run
Agent 1 — AI fixes all critical findings (dry-run = show diff only)
qcbot remediate ./tests --severity critical --commit --branch fix/auto
Agent 1 — same but writes to disk and git-commits on a new branch
qcbot suggest-rules ./tests --provider anthropic
Agent 4 — AI reads your code and proposes up to 6 new custom rules
qcbot pr-review --repo owner/repo --pr 42 --token ghp_…
Agent 2 — post inline findings as GitHub PR review comments
Browser UI
  • ⚙ Settings → paste API key → Save
  • Findings: Get AI fix on any finding  ·  ✨ Fix all critical for batch
  • Rules: ✨ Suggest rules to discover new ones from your codebase
Both engines work together. Engine 1 always runs first — instant scan, no key needed. Engine 2 is on-demand — triggered by you to explain, fix, or discover rules. Use Engine 1 alone if you just want the findings list. Add Engine 2 when you need AI-assisted fixes or custom rule discovery.

2Node.js CLI — quickest path
Prerequisites: Node.js 18 or higher — download at nodejs.org/en/download (choose the LTS version). No other installs required.
1
Install the CLI globally (one-time only)
This adds qcbot as a command you can run anywhere on your machine.
npm install -g @cqs/qcbot
Or skip the install and use npx for a one-shot run: npx @cqs/qcbot check ./tests
2
Run a quality check on your test folder
Point it at the directory that contains your spec / test files. Replace ./functional-tests with your actual path.
qcbot check ./functional-tests
Defaults: stack = playwright, threshold = 80, 4 parallel workers

Generate an HTML report (recommended)
Adds a self-contained report you can open in any browser and share with the team.
qcbot check ./functional-tests --report
Report saved to: ./qcbot-report/report.html — open it with open qcbot-report/report.html

3Python CLI & SDK
Prerequisites: Python 3.9+ and Node.js 18+. The Python package shells out to Node internally — the rule engine always runs in Node.js.
1
Install the Python package
The [cli] extra installs Click so the qcbot-py command is available in your terminal.
pip install "qcbot[cli]"
Library-only (no terminal command): pip install qcbot
2
Run from the terminal
Same flags as the Node CLI — just the command name changes.
qcbot-py check ./functional-tests --threshold 80 --report qcbot-py stacks
3
Use as a Python library
Import directly in any Python script, pytest hook, Django/Flask view, or Jupyter notebook.
from pw_quality import check

result = check("./functional-tests", threshold=80, report=True)

print(result.score)          # 72
print(result.passed)         # False
print(result.grade)          # "Fair"
print(result.summary.critical)  # 3

# Per-file breakdown
for file in result.files:
    print(f"{file.score:3}  {file.name}  ({file.critical_count} critical)")

# All critical findings
for finding in result.critical_findings:
    print(f"{finding.title} — {finding.file}:{finding.line}")
4
Add a quality gate to pytest (conftest.py)
from pw_quality import check, PwQualityError

def pytest_sessionfinish(session, exitstatus):
    try:
        result = check("./tests", threshold=80)
        if not result.passed:
            print(f"\n⚠  Quality gate FAILED — score {result.score} < 80")
    except PwQualityError as e:
        print(f"\n⚠  qcbot unavailable: {e}")

5GitHub Actions — automatic PR quality gate
Create the file .github/workflows/quality-pr.yml in your repository. The workflow runs on every pull request automatically — no secrets needed, GitHub provides the token. 
name: qcbot gate

on:
  pull_request:
    types: [opened, synchronize, reopened]

permissions:
  contents: read
  pull-requests: write   # needed for inline PR comments

jobs:
  quality:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: '20'

      - name: PR quality review
        run: npx --yes @cqs/qcbot pr-review \
          --stack playwright --threshold 80
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}

      - name: Full quality check
        run: npx @cqs/qcbot check ./tests --report --threshold 80
        continue-on-error: true

      - name: Upload HTML report
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: quality-report
          path: qcbot-report/report.html
          retention-days: 30
✓ Pass Score ≥ threshold → workflow approves the PR automatically
✗ Fail Score < threshold → inline comments posted on each finding line in the PR diff
↗ Report HTML report always uploaded as a build artifact (available for 30 days)
6Agentic AI features — all 4 CLI commands
What is agentic AI? These commands go beyond static analysis — they call an AI model (Anthropic Claude, Google Gemini, or AWS Bedrock) in a loop to understand your code, explain findings, and write fixes. You need an API key for features 1–3. Feature 4 (PR review) uses GitHub's own token.
🔑 API key setup is a one-time step. See Section 2 → Step 5 for the full walkthrough (provider table, Mac/Linux & Windows commands, verify step). Once set in your shell profile it works automatically for every command below — you never enter it again.
⏭ Skip if you only use Engine 1 — qcbot check runs the 59 predefined rules with no key at all.
AGENT 1 ✨ Remediation agent — bulk auto-fix
Scans all your test files, picks every finding that matches the severity filter, calls AI to generate a corrected version of each file, and writes the fixes to disk. Optionally creates a git branch and commit so it's easy to review as a PR.
a
Dry run — see what AI would change, write nothing
qcbot remediate ./functional-tests --severity critical --dry-run
Prints a before/after diff for each file without touching anything on disk
b
Apply fixes and auto-commit to a new branch
qcbot remediate ./functional-tests --severity critical --commit --branch fix/qcbot-auto
Set ANTHROPIC_API_KEY=sk-ant-… in your environment, or pass --api-key YOUR_KEY
c
Fix warnings too, using Google Gemini
qcbot remediate ./functional-tests --severity all --provider google --api-key YOUR_GOOGLE_KEY

⚠️ Safety rules — read before running without --dry-run
1
Only run against test files — enforced by --test-files-only ON by default
The agent has a built-in safety flag --test-files-only that is enabled by default. It checks every candidate file against recognised test-naming patterns (*.spec.ts, *.test.ts, test_*.py, *Test.java, *.feature …) and silently skips anything that doesn't match — even if you accidentally point the command at a mixed directory.
# --test-files-only is ON by default — no extra flag needed
qcbot remediate ./my-project --severity critical --dry-run
# → skips src/utils.ts, src/components/Login.tsx etc. automatically
# → only processes login.spec.ts, checkout.test.ts, test_api.py …

# To disable (only if you are certain the directory contains test files only):
qcbot remediate ./functional-tests --severity critical --no-test-files-only
⚠ --no-test-files-only active — AI may rewrite non-test files.
🖥 Browser UI  —  Settings → "Restrict AI fixes to test files only"
✓
🛡 Restrict AI fixes to test files only ON — recommended
✨ Fix all critical only processes *.spec.ts, *.test.ts, test_*.py, *Test.java … Production source files are skipped automatically.
🛡 Restrict AI fixes to test files only OFF — use with caution

Open Settings in the top bar → the toggle is always visible, independent of AI being on or off. The setting persists in browser localStorage across sessions.
✅ Safe by default. CLI requires explicit --no-test-files-only and prints a yellow warning when active. The browser toggle shows a yellow caution badge when off.
2
Always dry-run first — read the diff before applying
Run with --dry-run first. The terminal prints a before/after diff for every file it would change. Only apply if the changes look correct.
# Step 1 — inspect what AI wants to change (writes nothing)
qcbot remediate ./functional-tests --severity critical --dry-run

# Step 2 — if diff looks good, apply on an isolated branch
qcbot remediate ./functional-tests --severity critical --commit --branch fix/qcbot-auto
3
Human must review and test before merging — never auto-merge AI fixes
The agent commits to a new branch (fix/qcbot-auto). Raise it as a PR, run your full test suite against it, and have a team member review the diff before merging to main. If tests fail on the branch — do not merge.
Recommended workflow:
1. qcbot remediate ./tests --dry-run → review diff
2. qcbot remediate ./tests --commit --branch fix/qcbot-auto → AI applies + commits
3. Open PR: fix/qcbot-auto → main
4. CI runs your test suite on the branch → must pass ✅
5. Team member reviews the diff → approves
6. Merge only after step 4 + 5 pass
4
Rollback — how to undo AI fixes if tests fail
If tests fail on the AI-fixed branch, rollback is instant because the fixes are isolated to a git branch.
# Option A — delete the branch entirely (safest)
git branch -D fix/qcbot-auto
# main is untouched — nothing to undo there

# Option B — undo changes on disk without a branch (if you skipped --branch)
git checkout -- . # revert all AI-written files
git checkout -- tests/login.spec.ts # or revert one specific file

# Option C — already committed without a branch? revert the commit
git revert HEAD
This is why --commit --branch is the recommended default. It always leaves your main branch clean — rollback is just deleting a branch.
AGENT 2 ✨ PR review bot — inline GitHub comments

In GitHub Actions (auto-detected, no flags needed)
npx @cqs/qcbot pr-review --stack playwright --threshold 80
GitHub Actions sets GITHUB_TOKEN, GITHUB_REPOSITORY, and GITHUB_REF automatically — no manual flags required

── Rule ────────────────────────────────────────
PW-REL-001 · Hard wait detected · CRITICAL

── Why it's a problem ─────────────────────────
page.waitForTimeout(2000) pauses for a fixed 2 seconds regardless of

AGENT 4 ✨ Rule suggestion agent — discover & add new rules
AI reads a sample of your actual codebase and suggests custom rules specific to your patterns — things the built-in rules don't cover. Each suggestion includes the rule title, description, pattern to detect, and recommended fix.
a
Generate rule suggestions from your codebase
qcbot suggest-rules ./functional-tests --provider anthropic
Samples up to 8 files (1500 chars each), returns up to 6 rule suggestions
b
Save suggestions to a file, review & edit
qcbot suggest-rules ./functional-tests --provider anthropic --output my-rules.json
Writes rule definitions as JSON — edit titles, severities, or patterns before using
c
Or write a rule manually in JSON
Create custom-rules.json with your own rules:
[
  {
    "id": "TEAM-001",
    "title": "Prefer data-testid over CSS class selectors",
    "severity": "warning",
    "pattern": "\\.locator\\('\\.css-",
    "message": "Use getByTestId() — resilient to style changes"
  }
]
d
Apply your custom rules to any scan
qcbot check ./tests --custom-rules ./my-rules.json
Custom rules run alongside all 59 predefined rules — findings appear in the same report
e
Or use the browser UI
Rules tab → ✨ Suggest rules from codebase → each card has an Add rule button. Click Export JSON to download your full rule set (including custom rules) for use in CI with --custom-rules.

🗑 Removing custom rules
CLI — edit the JSON file and re-run
Open my-rules.json, delete the rule object you want to remove, save, then run:
# Remove TEAM-001 from the file, then verify it's gone:
qcbot check ./tests --custom-rules ./my-rules.json
# TEAM-001 findings will no longer appear
CLI — remove a specific rule by ID in one line
# Remove TEAM-001 from my-rules.json using node:
node -e "const fs=require('fs'); const r=JSON.parse(fs.readFileSync('my-rules.json')); fs.writeFileSync('my-rules.json', JSON.stringify(r.filter(x=>x.id!=='TEAM-001'),null,2));"

# Or disable a rule without deleting it — add "disabled": true:
# { "id": "TEAM-001", "disabled": true, … }

Rules tab → Custom rules section → click the 🗑 delete icon on any custom rule card → rule is removed immediately from the session and from localStorage. Click Export JSON afterwards to save the updated set for CI.
